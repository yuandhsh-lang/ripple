# Ripple 功能检查与修复报告

检查日期：2026-10-04，北京时间。最终状态：**PASS**，范围为 Ripple 本地代码检查、已确认 bug 的修复及本地验收；参赛交付仍有缺项。

## 基于什么开发

Ripple 是日历 × 天气场景的浏览器 Web 应用。实际安装版本与 package-lock.json 一致：React / React DOM 19.3.0、TypeScript 6.0.3、Vite 8.3.1；测试使用 Vitest 5.0.2，lint 使用 oxlint 1.86.0。当前环境为 Node.js 24.14.0、npm 11.9.0。

前端与业务规则都在本地 TypeScript 源码中，没有独立后端、模型 API 或 Octos 内核连接。天气冲突识别、时段搜索、审批、执行和验证由确定性规则驱动，不能据此声称具备大模型理解或完整的平台 Agent 能力。

开发宿主基线是 OctoSense-org/robrix2 的 `dev/wechat-octoscript-miniapps` 分支，锁定提交 `05daf9bdb05fafc6d8f04dcb312a35f1d46a661e`。本次重新读取 `.host/robrix2` 的 HEAD，与 `host-baseline.json` 一致。小程序走宿主已有的 Web URL 卡片入口；没有修改宿主 Rust 代码，也没有将 Ripple 改成 OctoScript 原生应用。宿主源码在 macOS/iOS 嵌入浏览器，在 Windows 提供外部浏览器打开入口。宿主登录、发送卡片和接收方打开仍未验证。

## 已修复的问题

1. **真实降水指标偏移一小时。** 原代码把时间戳处的降水量与概率放入后一小时。[Open-Meteo 定义](https://open-meteo.com/en/docs)明确它们描述前一小时，天气代码则描述瞬时状态。现在每个 `[t, t+1小时)` 区间采用 `t` 的天气代码和 `t+1小时` 的降水指标；最后一个缺少后继数据的区间及时间间隙不会被虚构为完整预报。
2. **雷暴漏判。** 原规则未识别 95、96、97、99，在降水估算较低时可能推荐雷暴时段。现在识别雷暴并阻止推荐，冲突原因和界面显示雷暴。
3. **演示日期与缓存失步。** 旧缓存跨日或超过 11:45 的演示切换点后，日历仍保留旧日期，而天气已切到新日期。现在两者使用同一个演示日规则；日期变化时重置样例，同一天的正常改期仍能持久化和回读。
4. **结构损坏的演示记录被当作有效数据。** 原代码仅检查 JSON 是非空数组。现在验证必要字段、起止时间、时长、数据来源与时区，坏记录恢复为可重复样例。
5. **无法提出改期时错误显示没有冲突。** 原界面只从提案读取影响，找不到可用时段就丢失冲突。现在单独保留已检测影响和目标活动，明确显示“发现冲突，暂无可用时段”，不进行写入。
6. **界面文案与实际状态不符。** 修正普通降雨统一被称为强降雨、任何活动成功后都称为网球、明天的演示称为今日、空日历仍显示读取中，以及没有后台监控却宣称持续关注的表述。

前五类问题均新增回归测试。修复前，第一批新增测试出现 9 项失败；降水时间对齐的第二批测试出现 3 项失败，其中包含调整后的既有归一化测试。修复后全部通过。
